# Contact identity and verification

The production HTTPS server boundary is now also exercised with real Locat login, private-key proof, provisioning, binding and revocation. See MATRIX_HTTPS_ACCEPTANCE.md for exact evidence and remaining browser limits.

Current implementation includes the explicit UI3 verification workflow and restricted gateway transport described below. Earlier groundwork sections are historical. Request-generation checks isolate late asynchronous results after cancellation; accepted contacts are paged in groups of 20 with no first-100 truncation. Full browser/native/recovery acceptance remains pending.

## Historical groundwork

Live peer-verification UI and protocol transport through the Locat gateway are not enabled yet. This checkpoint prepares identity authorization without adding Send, automatic trust, conversation mutation, federation or a second frontend.

A bound/proved browser can GET `/api/link/matrix/peer?accountId=<one-local-contact-id>`. The existing cookie/session/device proof boundary applies; the Matrix binding must belong to that current Locat session and remain locally authorized. Lookup is limited to 30 requests per account/minute and accepts exactly one 32-hex account ID. The returned local Matrix account mapping requires an accepted contact relationship and no block in either direction. Missing mapping, stranger, pending contact, removed contact and blocked contact produce the same unavailable result. The response contains accountId, matrixUserId and a requirement for client verification; it exposes no device pins, session tokens, trust assertion, presence or private profile. The mapping establishes a locally bound account relationship, not proof of a human identity.

The bootstrap Matrix gateway now limits keys/query and keys/claim to the bound account itself or a currently accepted, unblocked locally mapped contact. Batches are limited to 50 users; strangers, remote/unmapped accounts and malformed user maps are rejected before contacting the fixed upstream. Contact authorization is checked again before forwarding and after the response arrives, so a block/removal during an in-flight request withholds the response. Previously authorized upstream actions, including consumption of a one-time key, cannot be undone by a later block. Already downloaded public metadata cannot be erased from another client's memory. Other Matrix sync semantics have not been certified as contact-isolated; this is a key-discovery boundary only.

The isolated actual Synapse/SDK harness now accepts the synthetic Locat contact and checks the mapping before Matrix verification. It exercises actual m.sas.v1 to-device verification: transaction/peer identities match, SAS matches both peers, mismatch rejects both verifier promises and leaves device trust unverified, and a later successful flow requires both confirmations. One-sided confirmation does not finish either request. After mutual completion the test separately waits for both stored device trust results to be verified before the existing manual fingerprint check; request Done alone is not treated as a sufficient trust signal. This tests the actual SDK/Rust protocol over a synthetic loopback homeserver; the clients in that harness still access Synapse directly, not the entire HTTPS/proof gateway path.

Next integration must provide truthful account/contact selection, bounded verification request state, explicit matching/mismatch/cancel controls in UI3, peer/device-key continuity, standard protocol transport, expiration/cleanup and verified-trust rendering. It must not infer trust from this server mapping or manufacture SAS codes. Cross-signing, key backup, complete identity recovery, actual browser persistence, native clients and public federation remain pending. See MATRIX_HISTORY_KEYS.md for implemented local history import/export, which does not verify devices.

## Restricted SAS transport follow-on

The gateway now permits PUT only for the eight standard m.key.verification request/ready/start/accept/key/mac/done/cancel routes with bounded transport transaction IDs. Cookie, exact Origin, current Locat proof and bound Matrix bearer are mandatory. A request is at most 16 KiB and addresses one explicit active Matrix-bound Link device of this account or an accepted, unblocked contact. Wildcards, general encrypted to-device content, room keys and arbitrary event types remain gated. Authorization is rechecked before forwarding and before returning; a previously authorized upstream event cannot be recalled after a later block. Verification forwarding has a ten-second deadline within existing account rate/concurrency limits.

This is a routing/content boundary, not a second verification protocol: SDK/Rust owns transaction state, replay handling, key agreement, MAC validation, SAS and trust. Field validation ties from_device to the caller's binding, bounds request timestamps and permits only supported SAS negotiation. The pinned SDK advertises both legacy and current MAC names; the offer must include hkdf-hmac-sha256.v2 and acceptance must select it. Its standard accept event does not require a method field. Browser client setup now advertises only m.sas.v1. Cross-signing and QR UI remain pending.

Actual Synapse acceptance passes all eight emitted SDK message shapes through the production route/content validator and the SQL-backed active-device/contact predicate before the direct homeserver request. It still does not exercise the complete HTTPS cookie/proof gateway or provide live verification UI. Next wire explicit SDK start/sync and bounded request/confirmation/cancellation UI3 state without inferring trust from a Done event or the server mapping. Conversations remain gated.

## Live UI3 verification workflow

After binding the current device, setup now offers an explicit Enable device verification action. SDK sync is not started by opening settings or binding alone. Both people enable it and select each other from their accepted contact lists before either requests verification for an explicit bound device. Incoming requests from unselected senders are ignored by the presentation controller. Server authorization still applies to all transport operations; selection is an additional local consent boundary, not a substitute for it. The panel shows SDK-supplied decimal/emoji SAS and offers accept, matching-code confirmation, mismatch rejection and cancellation. It never generates comparison codes, calls setDeviceVerified, or treats the mapping/Done event as trust. Success additionally requires the same signing fingerprint and the SDK's stored verified status. Full identity/cross-signing recovery and Send remain separate.

The gateway now supports the SDK's own-user filter creation/retrieval, read-only push rules and capabilities. Filter creation is constrained to Locat's fixed verification profile; sync always substitutes that profile and offline presence regardless of client parameters. Room selection is empty, and the returned room, presence and account-data sections are cleared. Only standard verification to-device event types from the bound account or accepted local peers are returned. It does not expose a room timeline or general encrypted to-device transport. This verification-only profile intentionally is not a general Matrix frontend.

Peer discovery adds active bound device IDs without names/platform/pins, plus reverse resolution for one exact Matrix user ID; it retains current binding/proof and accepted/unblocked guards. Device IDs indicate current Locat authorization, not physical presence or current browser activity. Selection reads real authorized mappings; empty devices is a truthful unavailable state. The panel loads the accepted directory and renders 20 contacts per page with previous/next controls, including entries beyond the former first-100 cutoff. A shared UI3 Refresh contacts button retries temporary directory errors without restarting verification, resets the page and removes selections absent from the accepted directory. In-flight directory fetches abort on setup close. Server-side directory pagination remains separate work.

Compatibility dependency: matrixTrackedPeer.mjs isolates two internal hooks of the exactly pinned matrix-js-sdk 44.0.0 backend: its existing Rust tracked-user update and its outgoing-request processor. The public uncached device-info API downloads metadata without retaining it for SAS; room-free verification otherwise cannot find a previously unshared peer. The adapter uses WASM 18.9.0 UserId and changes neither cryptographic primitives nor trust. Missing runtime capabilities fail closed. Both library upgrades require rerunning actual gateway/SDK acceptance and reviewing the internal contract; this is not a universal SDK compatibility guarantee.

Verification lasts at most two minutes locally, with one active request. Contact/device authorization and signing-key continuity are rechecked before accepting/confirming and before verified display. The controller detaches listeners/timers on close and waits for outstanding SDK device operations before the parent releases its crypto-store lock. Cancellation is best effort when closing an aborted transport; the remote SDK may need to time out. SDK startup has a 20-second readiness deadline. SDK-managed optional RTC discovery remains gated by the gateway; this panel enables no call permission or media capture.

Validation now includes the actual UI controller on real SDK clients over the production HTTP Matrix gateway and Synapse: bound fresh devices, real stored trust on both sides after explicit confirmations, and no earlier room timelines in the verification client. Locat cookie/proof guards in that isolated harness are synthetic fixtures, while the Matrix bearer, gateway/store/validator, Rust engine and homeserver are real. It is not a production HTTPS/device-proof/browser acceptance run. Unit checks cover explicit startup, user-selected incoming requests, inactive recipients, mismatch, trust-persistence delay, pending-read cleanup, unavailable adapter and UI confirmation controls. Actual browser IndexedDB/disk persistence and native/public acceptance remain pending.
