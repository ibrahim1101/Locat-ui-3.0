# Contact identity and verification groundwork

Live peer-verification UI and protocol transport through the Locat gateway are not enabled yet. This checkpoint prepares identity authorization without adding Send, automatic trust, conversation mutation, federation or a second frontend.

A bound/proved browser can GET `/api/link/matrix/peer?accountId=<one-local-contact-id>`. The existing cookie/session/device proof boundary applies; the Matrix binding must belong to that current Locat session and remain locally authorized. Lookup is limited to 30 requests per account/minute and accepts exactly one 32-hex account ID. The returned local Matrix account mapping requires an accepted contact relationship and no block in either direction. Missing mapping, stranger, pending contact, removed contact and blocked contact produce the same unavailable result. The response contains accountId, matrixUserId and a requirement for client verification; it exposes no device pins, session tokens, trust assertion, presence or private profile. The mapping establishes a locally bound account relationship, not proof of a human identity.

The bootstrap Matrix gateway now limits keys/query and keys/claim to the bound account itself or a currently accepted, unblocked locally mapped contact. Batches are limited to 50 users; strangers, remote/unmapped accounts and malformed user maps are rejected before contacting the fixed upstream. Contact authorization is checked again before forwarding and after the response arrives, so a block/removal during an in-flight request withholds the response. Previously authorized upstream actions, including consumption of a one-time key, cannot be undone by a later block. Already downloaded public metadata cannot be erased from another client's memory. Other Matrix sync semantics have not been certified as contact-isolated; this is a key-discovery boundary only.

The isolated actual Synapse/SDK harness now accepts the synthetic Locat contact and checks the mapping before Matrix verification. It exercises actual m.sas.v1 to-device verification: transaction/peer identities match, SAS matches both peers, mismatch rejects both verifier promises and leaves device trust unverified, and a later successful flow requires both confirmations. One-sided confirmation does not finish either request. After mutual completion the test separately waits for both stored device trust results to be verified before the existing manual fingerprint check; request Done alone is not treated as a sufficient trust signal. This tests the actual SDK/Rust protocol over a synthetic loopback homeserver; the clients in that harness still access Synapse directly, not the entire HTTPS/proof gateway path.

Next integration must provide truthful account/contact selection, bounded verification request state, explicit matching/mismatch/cancel controls in UI3, peer/device-key continuity, standard protocol transport, expiration/cleanup and verified-trust rendering. It must not infer trust from this server mapping or manufacture SAS codes. Cross-signing, key backup, complete identity recovery, actual browser persistence, native clients and public federation remain pending. See MATRIX_HISTORY_KEYS.md for implemented local history import/export, which does not verify devices.

## Restricted SAS transport follow-on

The gateway now permits PUT only for the eight standard m.key.verification request/ready/start/accept/key/mac/done/cancel routes with bounded transport transaction IDs. Cookie, exact Origin, current Locat proof and bound Matrix bearer are mandatory. A request is at most 16 KiB and addresses one explicit active Matrix-bound Link device of this account or an accepted, unblocked contact. Wildcards, general encrypted to-device content, room keys and arbitrary event types remain gated. Authorization is rechecked before forwarding and before returning; a previously authorized upstream event cannot be recalled after a later block. Verification forwarding has a ten-second deadline within existing account rate/concurrency limits.

This is a routing/content boundary, not a second verification protocol: SDK/Rust owns transaction state, replay handling, key agreement, MAC validation, SAS and trust. Field validation ties from_device to the caller's binding, bounds request timestamps and permits only supported SAS negotiation. The pinned SDK advertises both legacy and current MAC names; the offer must include hkdf-hmac-sha256.v2 and acceptance must select it. Its standard accept event does not require a method field. Browser client setup now advertises only m.sas.v1. Cross-signing and QR UI remain pending.

Actual Synapse acceptance passes all eight emitted SDK message shapes through the production route/content validator and the SQL-backed active-device/contact predicate before the direct homeserver request. It still does not exercise the complete HTTPS cookie/proof gateway or provide live verification UI. Next wire explicit SDK start/sync and bounded request/confirmation/cancellation UI3 state without inferring trust from a Done event or the server mapping. Conversations remain gated.
