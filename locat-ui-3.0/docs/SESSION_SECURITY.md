# Local session security

Account settings can refresh the actual session list, revoke individual sessions through the existing action and now sign out the other active Locat sessions while preserving the current one. The bulk action opens the existing UI3 Sheet and requires an explicit password submission through the shared TextField and submit Button. Opening the sheet makes no mutation. Submission success removes the other rows and reports the server's actual revoked count. Failure preserves the rows and displays the error. The confirmation password clears after each attempt and when the sheet closes.

POST /api/auth/sessions/revoke-others accepts exactly currentPassword, a nonempty string of at most 256 characters. It requires an authenticated cookie and the exact trusted Origin, bounds JSON through the existing parser, verifies the password with the existing scrypt parameters and applies a separate five-attempt/account/minute limit. No requested user/session identifier can override the server-selected owner/current cookie.

After verification, a SQLite write transaction rechecks that the initiating session remains live and that the account's password verifier is unchanged. It expires local Matrix grants bound to the other active sessions, removes those sessions and inserts the audit event together. Audit failure rolls back the entire operation. The current session and other accounts are preserved. Counts cover active sessions at commit; sessions created later are not prevented. Expired records are excluded from the active count and retain the existing login-time cleanup policy. No new database schema is required.

Password changes now have the same commit-time live-session/verifier check after both derivations. New password hashing occurs outside the process serialization queue; the final SQLite transaction checks authorization, changes the verifier, expires this account's local Matrix grants, removes its Locat sessions and writes its audit event atomically. A session revoked during derivation cannot commit a credential change.

Cookie authorization rejects revoked sessions on subsequent requests. The existing WSS health connection rechecks its session on messages and heartbeat, closes unauthorized connections with 4001, and does not expose chat/module payloads. Already authorized/completed actions and downloaded data cannot be undone. Volatile Link proofs do not bypass the required Locat cookie/session checks.

These operations revoke local Locat authorization. They do not delete every upstream Matrix token, revoke a persistent Link identity, wipe browser/native keys, recall files, change separate Vault/Secrets passphrases or certify physical-device state. Use the separate managed Matrix/Link revocation controls for their documented scopes. MFA, biometric/native protection, full recovery, actual browser acceptance and upstream account-wide token policy remain pending.

Backend tests cover owner/current/foreign isolation, grant expiry, password/Origin/input rejection, rate limits, revocation during derivation, stale verifier rejection, password-change session policy and audit rollback. UI tests require explicit confirmation and verify failure/secret cleanup. Actual HTTPS/Synapse acceptance uses real scrypt login, fixture-trusted TLS, other-cookie rejection and actual WSS closure while preserving current and foreign sessions. This is not real browser or native acceptance.
