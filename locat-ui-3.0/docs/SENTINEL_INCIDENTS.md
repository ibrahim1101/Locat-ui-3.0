# Sentinel incident search and paging

The live UI3 Incidents section loads 25 account-owned incidents per page. Search titles/descriptions/source text, select a status and severity, optionally enter an exact source, and choose Apply incident filters. Draft fields do not affect existing requests until applied. Load older incidents continues the current applied query; Refresh starts again from the newest retained matches. Shared UI3 controls, typography, sheets and theme tokens are preserved.

GET /api/sentinel/incidents retains its incidents array and adds nextCursor. The default page remains 100 for existing consumers, with limit 1–100. Optional filters are q (160 characters), status (open/acknowledged/resolved), severity (info/low/medium/high/critical), exact source (64 characters), and before. Unknown/duplicate query fields, including account selectors, are rejected. Every SQL query includes the authenticated owner. Search uses literal parameterized instr matching, not SQL wildcard interpolation; SQLite lower handles ASCII case folding and exact non-ASCII text remains searchable. Source equality is case sensitive.

The opaque-to-the-client cursor uses a strictly validated nonnegative epoch-millisecond timestamp and a 32-character lowercase hex incident ID. Rows order by updatedAt descending then ID descending; the next page compares that exact pair. This reaches beyond the former newest-100 cutoff and handles tied timestamps. It is not a frozen historical snapshot: webhooks and actions can move incidents above a previously received cursor. Refresh to include changed/new incidents. The UI deduplicates loaded IDs; no stable snapshot, immutable incident evidence or complete export is claimed.

List requests have a 15-second fetch/body deadline, cancellation and generation checks. Applied filter/refresh changes cancel old requests; late older pages cannot attach to a replacement list. Older-page errors retain already loaded rows and their cursor for retry. Incident detail/actions use separate cancellation/generation and duplicate-action guards so a closed or replaced sheet does not reopen on a late response. Writes are not automatically retried; a timed-out action may have committed and requires refresh.

The whole Sentinel state is keyed by the signed-in account. Changing account/logout drops incident, token-sheet and one-time-token state; explicit local mode makes no Sentinel requests. Token creation has synchronous duplicate exclusion and a sheet generation check, preventing a late response from restoring a closed token display. Source integrations still use existing generic/nscout/pipelineguard adapters. Integration token inventory and per-incident history now have their own cursor pages, described below. Monitoring agents, notification delivery and retention policies remain open.

Tests cover more than 100 owner records, timestamp ties, new arrivals during paging, literal special-character search, combined filters, foreign-owner exclusion, malformed/ambiguous queries, and updated-row refresh behavior. UI tests cover applied-vs-draft queries, ID deduplication, stale-page cancellation, failed-page retry, unmount, local mode and account-state reset; actual HTTP API tests retain ownership/Origin/action behavior and validate query rejection. These Node/jsdom checks do not certify physical browsers, native devices, vendor webhook acceptance, full monitoring or the complete roadmap. No schema migration, public service or alert deletion was performed.

## Mutation authorization and audit ordering

Webhook authentication is checked again inside the ingestion write transaction by exact integration-token ID, owning account and non-revoked state. Revoking a token while an authenticated request body is still arriving prevents that request from creating/updating an incident or appending history. A commit ordered before revocation remains committed; revocation does not erase retained alerts.

Token creation/revocation and incident actions read at most 4096 bytes, reject extra selector fields, recheck the Locat session after body reading and pass a server-derived session digest into SQLite. After obtaining BEGIN IMMEDIATE they check that the session still belongs to the account and has not expired. Token creation enforces the existing 20-active-token cap in that same transaction. The data mutation and a metadata-only account audit event commit together. Incident action history is in the same transaction too. Audit failure rolls back minting/revocation/status/history changes. The existing direct maintenance store signatures remain available without an HTTP session context; ordinary HTTP callers cannot select that behavior.

User mutations share a 60-action/account/minute bucket in addition to the 20-created-token/account/hour limit. Webhooks retain their separate 120/token/minute bucket. Audit entries contain action names, not raw bearer tokens, incident titles, descriptions or note contents. Synthetic tests cover paused-body token/session revocation, stale/mismatched token snapshots, expired/foreign/revoked sessions, audit rollback and bounded mutation requests. These tests do not certify native agents, vendor payload acceptance or independent security review.

## Integration inventory and per-incident history pages

Integrations is loaded only when selected. It starts with Active tokens, with Revoked tokens and All integration tokens views. Each page requests 25 metadata records. Load older integration tokens continues the applied state filter; filters and refresh cancel old page reads. This prevents the previous newest-100 mixed list from hiding an old active token behind many revoked tokens. Cards show public prefixes, creation time, last-use time and revocation state; raw token values are still available only once at creation. The API retains its tokens array and adds nextCursor, with default 100, limit 1–100, state active/revoked/empty, and a validated createdAt+ID before cursor. Every query is owner-bound and selects only public metadata; hashes and raw tokens are never listed.

Incident detail now requests 50 events and offers Load older incident history. GET /api/sentinel/incidents/:id retains incident/events and adds nextCursor. Its default remains 200, limit is 1–200 and before is a canonical positive safe event ID. Events are joined to the owning incident/account on every page. New events above the cursor do not disrupt older paging; close/reopen to include new history. Successful actions reload the newest page. Older-page failures keep displayed notes/cursor for retry, and repeated IDs are deduplicated. Closing a sheet or changing account invalidates late responses.

Both APIs reject unknown, duplicate and foreign-selector query parameters. No records are deleted or changed by paging. Token creation/revocation can change filter membership; refresh to reflect changes from other clients. The creation cap and one-time response semantics remain unchanged; a lost creation response can leave an active token whose secret cannot be recovered, so the UI instructs users to refresh/revoke an unwanted token rather than silently mint again. These are browser UI/API source tests, not physical device/vendor acceptance or a retention/archive/export system.

Tests cover 132 tokens with older active entries behind more than 100 revoked rows, public metadata-only pages, filters/ownership and invalid queries; 231 owned incident events interleaved with foreign history and a later arrival; actual HTTP token/history cursor validation; UI older-note retry/deduplication; active/revoked inventory filters; and duplicate creation/late-dialog-close handling.

## Loaded incident JSON download

The UI3 incident panel now offers Export loaded incidents after results have loaded. This explicit action creates readable JSON in this browser; descriptions and titles may contain sensitive operational information. It exports only loaded public incident fields (ID/title/description/source/severity/status/occurrences/updatedAt), the applied search/status/severity/source filters, export time, record count and hasMore. Draft filters do not alter the export selection. Extra owner/fingerprint/token fields and per-incident notes/history are excluded. No extra server fetch, automatic background enumeration or upload occurs.

Load older incidents first to include them. Mutable cursor ordering still does not provide a frozen or complete archive. Exports reject empty/duplicate/malformed data, more than 10,000 loaded records or more than 8 MiB actual UTF-8 JSON; oversized output is rejected rather than silently truncated. This is not an encrypted backup, signed evidence, retention policy, full event history or complete account export. Browser download storage and its copies remain user-managed.

Unit/DOM tests cover exact field selection, filter/cursor metadata, draft exclusion, hidden-field omission and Unicode byte limits. A separate isolated Chromium target exercises actual token creation, webhook ingest, incident note/resolve, downloaded JSON and token revocation; it passed in actual Chromium at 213a92c, workflow 38751797265 / job 116479806942 (all six browser tests passed). See BROWSER_FOUNDATION_ACCEPTANCE.md.

All live Sentinel incident/token/activity panels now attach their keyed account ID as X-Locat-Account. The server rejects a mismatch with the cookie-derived owner, preventing a stale tab from rendering a newly signed-in owner's records under the old account label. This optional consistency guard does not replace authorization or alter webhook token ownership.
