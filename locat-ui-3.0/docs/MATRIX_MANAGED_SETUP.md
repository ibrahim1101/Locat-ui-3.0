# Managed setup before binding

Schema 14 adds matrixManagedDevices so a managed Matrix session is not invisible to cleanup merely because browser initialization or public-key binding never finished. The server records the local account/Link ID, deterministic Matrix user/device, operation lease and timestamps before any upstream registration/login. There is no raw token, password, private key, service secret or session cookie in the record. Matrix status returns only the recorded identifiers and whether an operation is active; its private operation token is not returned.

Beginning setup reserves the deterministic managed Matrix account association. It does not prove that the upstream account was created and grants no Matrix gateway authorization, peer-device availability, crypto trust or conversation access. Public-key binding remains mandatory. Existing foreign/manual account or device associations are rejected rather than migrated or overwritten. Subsequent binding must match a recorded managed identity exactly.

Setup and explicit managed-device deletion acquire a transactional 60-second per-device operation lease shared across processes. Another operation is rejected while it remains active. Authorization and the lease are checked between network stages; the existing provisioning network deadline is ten seconds, with a separate bounded token-cleanup attempt on failure. Normal settlement releases only its own operation token, so stale completion cannot clear a replacement lease. This is local serialization, not a transaction or fencing token implemented by the remote homeserver.

Link revocation queues either the completed binding or the recorded unbound managed device in its existing transaction. The worker skips an active operation lease. A crashed operation becomes eligible after lease expiry. If a delayed operation later settles after a previous worker deletion, settlement re-arms cleanup and invalidates stale worker completion. The worker still validates the revoked Link identity, queued target and exact derived managed identity before contacting Matrix. Failures remain pending with the existing durable backoff. No remote rollback or instantaneous deletion is asserted.

An authorized owner can use the existing Revoke this managed Matrix device action even when setup never bound public keys and the browser no longer retains its token. The command contains no Matrix token: the server derives and validates the recorded device and uses its existing restricted application-service credential. UI3 displays a truthful prior-attempt explanation, and failed managed setup refreshes status so this action can appear without closing/reopening the sheet. A successful response is required before UI confirmation. A recorded attempt may have no active upstream token at all; the UI does not invent an active-session count.

Tests cover cross-connection exclusion, lease expiry/replacement, stale settlement, immutable identity, missing tracking, v13 migration with preserved bindings, unbound Link cleanup, failure after token issuance, failed immediate logout and late deletion re-arming. Actual HTTPS/Synapse acceptance issues normal managed tokens without binding, confirms no gateway grant, then proves explicit device deletion and queued Link deletion invalidate the corresponding tokens upstream. Database/WAL raw-secret checks include those accounts. Browser UI tests use mocked transport; actual browser/native persistence and UI acceptance remain separate.

Schema 14 cannot discover unrecorded sessions issued before this migration. Account-wide token enumeration/revocation, independent review, full identity/cross-signing recovery, browser/native acceptance and public federation remain pending. The original requirement register and full master roadmap are retained. No public service/operator configuration was changed and conversations remain gated.


## Known-device state in Devices

The existing proof-authorized Link snapshot now includes the owner's known Matrix device identifier, whether managed setup is recorded, whether an operation is active, and local binding state. Grant authorization requires both an unexpired stored binding and an existing unexpired Locat session. A missing/revoked session or expired grant is reported as blocked; a setup without binding is unbound. A revoked Link identity cannot be authorized. Only public status metadata is returned; operation tokens, session hashes and Matrix bearer tokens are omitted. UI3 displays this in the existing device cards beside the separate cleanup status.

This is the local device/grant inventory, not upstream token enumeration or an online/physical-device guarantee. A Matrix token can independently expire or be revoked upstream. Tests exercise setup, binding, Locat logout and account isolation, and the actual HTTPS harness checks both unbound and authorized snapshots.
