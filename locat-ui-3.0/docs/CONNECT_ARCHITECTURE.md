# Locat Connect architecture

The existing UI3 app and Node/SQLite server remain the platform. Browser accounts, cookies, IndexedDB keys and module APIs are isolated by origin. Server selection opens a validated HTTPS origin; it does not forward a cookie/token or migrate keys across origins. Do not add per-module alternate backends. Native configurable-server transport will reuse discovery but requires its own secure cookie/key lifecycle acceptance.

GET /.well-known/locat is a bounded, public version-1 discovery contract with instance UUID, exact origin and truthful capabilities. Wildcard CORS applies only to this public response and carries no credentials. UUID persists in SQLite schema 11 and its backups; it is not a cryptographic server identity. Restoring a clone preserves UUID: do not run independent writable clones as one identity. TLS plus operator address verification is currently the server trust boundary.

Direct TLS remains the LAN option. Optional TLS-termination mode accepts only exact configured socket IPs and one HTTPS Host/Origin; forwarded headers never select the origin. Authentication rate limiting uses the proxy socket address unless `LOCAT_PROXY_CLIENT_IP_HEADER` explicitly opts into one single-valued client-IP header from that trusted peer. Isolate the HTTP hop using loopback or a dedicated private container network with no published port. The terminating proxy is trusted to preserve HTTPS/Host and, if client attribution is enabled, overwrite the chosen header. Other tenants must not access that network.

Connection monitor: one readiness fetch at a time, 5-second abort, 15-second healthy checks, exponential jittered retries capped near 30 seconds, online/offline and visibility events, cleanup on unmount/local mode. Readiness never creates or removes an account. Session health WebSockets, safe session inspection and qualified local addresses are now connected; synchronization and durable notifications remain pending. Existing Link/Remote proof and encryption boundaries remain distinct from messaging.

## Session real-time channel and addresses

/api/connect/socket uses pinned ws 8.22.0 on Node and native browser WebSocket. Exact Host/proxy socket peer/Origin and session cookie are required; no query token or module/chat messages are accepted. Limits: 256 sockets total, eight/account, 60 upgrades/minute/socket peer, 1024-byte inbound frame, five application frames/second/socket, 8 KiB outbound-buffer ceiling; compression disabled. Server rechecks session and pings every ten seconds, terminating missing-pong clients on the next heartbeat and closing expired sessions with 4001. Device proof remains separate: this health channel does not authorize sensitive module subscriptions.

Browser five-second ready deadline, 15-second ping/ten-second reply timeout, jittered exponential retry and cleanup/network handling are connected. Diagnostics separates HTTP readiness and real-time health. Session inspection distinguishes confirmed 401 from network/5xx, preserving an existing identity during outage without granting server access. A confirmed session-expiry closes the local session. Real-network WSS remains unverified.

Explicit LOCAT_PUBLIC_ORIGIN enables LC-code@authority and locat://authority/account/immutable-id plus instance UUID in profiles. Qualified searches only resolve that exact authority; remote authorities return 501 before any outbound request. Existing LC/account IDs remain unchanged; without a configured canonical origin no qualified address is advertised. An optional owner-only Ed25519 key file signs versioned server and account claims; the browser verifies both in nested identity details and supports explicit per-account, per-origin fingerprint pins. The signatures do not prove authority ownership; first-contact trust requires a separate fingerprint comparison. Rotation/recovery, stronger platform storage, and federation remain future work. See GLOBAL_IDENTITY_THREAT_MODEL.md.

Shared proved-device ICE configuration and opt-in Remote wiring are implemented as specified in CONNECT_NETWORK_TRAVERSAL.md; no external server or relay is configured by default. Calls/Link may reuse this service only with their own consent and permission boundary.
