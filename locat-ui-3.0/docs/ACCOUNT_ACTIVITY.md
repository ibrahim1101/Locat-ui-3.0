# Searchable account activity

Sentinel's account activity section now fetches its own real account audit data when selected. It reuses UI3 TextField, Button, Badge, StateView and existing card/theme tokens. Search/severity changes are applied explicitly; the current result set resets on a new filter or refresh. Older events append by ID without duplicates. Refreshing the Sentinel header while this section is selected refreshes activity rather than unrelated incident/token requests.

GET /api/security/events remains cookie-authenticated and owner-bound. Its existing events field is retained; nextCursor is an additive string/null field. Default page size remains 100 for existing callers; UI3 requests 25. Optional parameters are q (trimmed event-name search, at most 80 characters), severity (info, warn, error), before (canonical positive safe-integer event ID), limit (1–100), fromTime (inclusive epoch milliseconds) and toTime (exclusive epoch milliseconds). Time bounds are optional canonical nonnegative safe integers within the JavaScript Date range, with fromTime strictly less than toTime when both are present. UI3 local date/time inputs are converted to epoch milliseconds before submission. Duplicate/unknown keys, foreign account selectors, invalid severities and malformed/oversized cursors/pages return 400. No client account ID influences ownership.

SQLite uses bound literal substring matching on raw event names and their period-to-space display names; percent/underscore characters have no wildcard meaning. The warning filter includes legacy warn and warning rows without rewriting history. Results use descending unique audit IDs and before-ID cursors, so new events arriving above the current page do not duplicate or skip the retained older sequence. Search is over audit event names, not document contents or incident notes. Every older page reapplies ownership and filters.

The panel has a 15-second request deadline. It aborts obsolete/in-flight work on filter/refresh/unmount and ignores stale responses by request generation. Older-page errors preserve already loaded rows and the cursor for retry. First-page errors show an honest error and refresh control; no preview/fake events are inserted. An exhausted result has no continuation cursor.

Tests exercise more than 100 retained events, new inserts during paging, owner isolation, literal search, severity aliases, query bounds, explicit filter submission, retry, stale-result suppression, pending-request abortion and Sentinel tab/header wiring. The actual HTTPS/Synapse harness checks search for the newly generated bulk-revocation audit event, foreign-account isolation and rejection of malformed/foreign-selector queries. Local unit/browser-rendering tests do not certify actual browser/native acceptance.

No schema migration, audit erasure, external notification or public service activation is added. Retention policy, full-account/archive export and the wider cross-module Timeline remain future work. Existing browser/native/full identity-recovery and messaging gates remain unchanged.


## Loaded-result JSON download

Export loaded activity performs no additional network request or server mutation. It serializes the currently loaded records and applied filters after an explicit click. A changed search/severity/date draft is excluded until applied. Its version-1 locat.account-activity envelope includes export time, record count, loaded-events scope, fromTime/toTime in epoch milliseconds, hasMore and only id/event/severity/createdAt for each event. From is inclusive and to is exclusive. hasMore marks older matching records not yet loaded. Live history can change; this is not a transactionally signed snapshot or forensic chain-of-custody artifact.

The formatter rejects empty, malformed, duplicate or oversized collections, more than 10,000 records and UTF-8 JSON exceeding 8 MiB. It never silently drops rows to meet a limit. Readable JSON is prepared through a temporary Blob URL and the native browser download flow; the URL is released after the existing download grace interval. UI confirmation means the download was prepared, not that the browser saved it to disk. Real browser/download acceptance remains pending.

Tests cover inclusive/exclusive boundaries with paging and account isolation, strict invalid ranges, local-input conversion, explicitly clicked download, applied-versus-draft filters, unexpected-property exclusion and the exact Blob JSON content. UTF-8 size limits are tested with multi-byte records. The actual HTTPS harness checks that the generating account can query the event at its exact start timestamp, that an exclusive end excludes it and that an empty/inverted range is rejected.
