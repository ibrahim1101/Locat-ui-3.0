# Experimental paired browser screen viewing

UI3 Remote connects account-owned Link identities and pinned, dual-confirmed pairs to consented browser screen viewing. It does not embed the original unthemed standalone host/client or claim native desktop input control.

A proved viewer requests its verified paired source device. The request expires after 60 seconds. Only the source device can approve/deny. Approval starts only after an explicit UI click opens getDisplayMedia with video enabled and audio disabled and the user chooses a surface. No persisted display-capture permission or automatic startup is used. Picker cancellation or failed peer/session setup stops any acquired tracks.

Schema v9 stores owned session metadata and opaque encrypted signaling. SDP offers/answers and ICE candidate payloads are encrypted/authenticated with the pinned pair key, fresh AES-GCM IVs and context binding account, pair, session, signal ID, device direction and signal kind. Only the host may send an offer and only the viewer may answer; both proved actors may send ICE. Destination lists exclude its own signals and use monotonic cursors. Signals are bounded at 64 KiB plaintext, 512/session, eight pending/active sessions/account, with the existing command/chunk rate bounds. Active sessions expire after twenty minutes. Close, expiry, pair rejection and device revocation remove active signaling ciphertext and preserve session metadata.

The browser defaults to direct ICE without external servers. An explicit per-client UI3 switch can use operator-configured STUN/TURN; optional relay-only fails if TURN is absent. Temporary credentials require a current session and device proof. See CONNECT_NETWORK_TRAVERSAL.md for settings, bearer-credential lifetime and privacy/abuse limits. No actual NAT traversal or relay allocation has been verified; many network/platform combinations may still fail. No audio, native keyboard/mouse injection, remote filesystem access, unattended capture, auto-approval or silent recording is implemented.

Local capture/peer resources stop on explicit Stop, track end, timeout, local route exit/logout, closed/expired server session or signaling/authorization failure. Peer close/revocation is observed through polling (two-second signaling; five-second UI status); network calls time out after fifteen seconds. A delayed/suspended/malicious client may ignore revocation, and already received frames/copies cannot be recalled. Browser capture indicators and OS/browser selection behavior remain authoritative.

Verified automated coverage includes actual cryptographic signaling relay/decryption, metadata/context tamper rejection, source-only consent, signal roles, expiry/revocation purge, explicit capture-picker ordering, no local-mode network/capture, and track/peer cleanup on failure. WebRTC/capture methods are mocked in DOM tests. No actual two-device stream, browser pixel/codec behavior, native control, Android capture permissions or TURN acceptance is claimed. The native Windows host reference in original Locat remote/ remains read-only and requires separate authenticated adapter/consent integration.

Primary standards checked during implementation: W3C Screen Capture (https://www.w3.org/TR/screen-capture/, current working draft) and WebRTC (https://www.w3.org/TR/webrtc/). This does not imply certification or independent protocol security review.
