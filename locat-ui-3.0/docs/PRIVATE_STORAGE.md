# UI 3.0 encrypted private storage

Vault and Secrets are experimental browser implementations adapted from original Locat's private-store design. They are separate from messaging encryption and native secure storage. All controls use the UI 3.0 theme. Authenticated account cookies and the trusted request Origin authorize writes; explicit local mode has no server storage access.

## Current behavior

Each account has independent Vault/Secrets stores. A random 256-bit master key is wrapped by a passphrase-derived AES-GCM key using PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt). Each wrapping/entry operation generates a fresh 12-byte IV and uses a 128-bit authentication tag. Additional authenticated data binds the UI3 protocol namespace, account ID, module, store ID and record ID. Raw master-key byte arrays are cleared after import; imported master keys are nonextractable. Passphrases and plaintext entry names/content are never submitted to the server by these flows.

Server SQLite stores only configuration, wrapped master key, ciphertext envelopes, opaque IDs, revisions, ciphertext sizes and modification timestamps. That metadata reveals account association, entry counts, sizes, timing and access patterns. Private action audit events contain action/module names only, not decrypted names or contents.

Vault imports one file up to 2 MiB, encrypting names, folder labels, MIME and bytes together. Decrypted copies download as application/octet-stream. Secrets supports credentials/notes, masked password fields, unbiased CSPRNG password generation, editing and explicit clipboard copying. Folder/name editing and search run only on decrypted client memory. The server never indexes decrypted names or searches private plaintext.

Limits: 128 objects/module/account, 64 MiB serialized ciphertext quota/module/account, 4 MiB envelope data, 60 writes/minute/account. Ownership and module scoping apply to every read/write/delete. Expected-revision checks reject stale overwrites/deletes; quotas and object counts are enforced transactionally. Store identity replacement/reset is not exposed. A separate passphrase-change action can replace only the wrapping configuration for the same store ID. A forgotten passphrase cannot be reset using the login password.

Lock now, hidden-page handling and five-minute idle locking drop key/plaintext references and clear forms/dialogs. The screen is keyed by exact account ID and module, so logout, account replacement or Vault/Secrets switching mounts a fresh locked state and removes previous records, editors, forms and status. Unmount invalidates in-flight operations. A synchronous operation guard excludes duplicate submissions even before disabled controls render; generation checks keep old completions from changing a replacement operation or a later post-restore status refresh. Already-dispatched server writes may still commit; this is not transactional cancellation. Browser JavaScript does not guarantee secure erasure of prior immutable strings, garbage-collected memory, clipboard history, downloads or OS/browser remnants. Copy and decrypted download are explicit user actions. Native biometric unlock/hardware key storage is not connected.

## Backup and restore

Download encrypted backup contains configuration, opaque scope IDs and ciphertext only. Restore validates the exact format/scope/schema/bounds, unlocks with the original passphrase and decrypts/authenticates every archived object before the first write. It restores only missing IDs into the matching account/module/store, preserving all existing entries/configuration. An empty matching-account store may initialize from the backup configuration. Scope is tied to stable UI3 account IDs rather than hosting origin, so moving the same database to another trusted HTTPS origin does not require re-encryption. Restoring into a newly created different account is rejected.

Restoration is a sequence of revision-checked writes, not an atomic whole-backup import. Interruption, concurrent writes, hidden-page locking, server capacity or rate limits may leave a subset restored; a retry rechecks live status and safely skips existing IDs. A large archive may require waiting for the 60/minute write bucket to reset and retrying. Unlock again after completion. SQLite online backups also preserve the encrypted stores; restore the same account database using server recovery instructions.

Original Locat numeric-account/origin-bound encrypted envelopes and UI3 string-account envelopes use different authenticated scopes. They are not silently imported or declared byte-compatible. The original repository and its data remain untouched. A verified decrypt/re-encrypt migration tool is still required for original encrypted-store imports, different accounts, and full encryption-key rotation.

## Verification and limits

Tests use actual Node Web Crypto for create/unlock/encrypt/decrypt, nonextractability, fresh IVs, tampering, owner/module/store/record mismatch and file length validation. UI tests verify no plaintext/passphrase in uploads, locked-page clearing, scoped local search, safe missing-only restore, corrupted archive rejection before writes, account/module plaintext-state reset and duplicate form-write exclusion. SQLite/API tests verify isolation, schema migration, revision conflicts, count/byte quotas and trusted Origin. These assertions do not replace browser/native acceptance or an independent security review.

The browser client and origin must be trusted: a malicious delivered client, XSS, compromised device, extension or unlocked session can read plaintext. This is not an audited password-manager product or a claim that a malicious server cannot replace the browser client. Large-file streaming, offline encrypted replicas, autofill, shared vaults, native keychain/keystore integration, full encryption-key rotation and original-store migration remain open.

## Change a private-store passphrase

While unlocked, choose **Change store passphrase**, enter the current private-store passphrase and confirm a different new passphrase (15–1024 characters). The existing UI3 Sheet/TextField/Button controls are used. The browser authenticates and decrypts the current wrapped 32-byte master key, then wraps that same key with the existing PBKDF2-HMAC-SHA256/AES-GCM format using a fresh random salt and IV. Raw master-key bytes are cleared in a finally block. Entries, ciphertext, IDs, revisions and store identity do not change, and neither passphrase nor the raw key is sent to the server.

POST `/api/private/vault/rewrap` or `/api/private/secrets/rewrap` accepts exactly `{expectedConfig, config}`. It requires the current cookie, exact trusted Origin, the existing private-write rate limit and a 4096-byte request limit. Private writes recheck the session after body reading. Rewrap additionally checks the hashed session against the live account/expiry **inside BEGIN IMMEDIATE**, after obtaining the SQLite write lock. The current stored wrapping config must equal expectedConfig, independent of JSON property order. The new config must retain the same store ID and have different salt/IV/wrapped bytes. The config update and `private.<module>.passphrase.changed` warning audit commit together; an audit failure rolls everything back. Concurrent/stale changes return 409 without overwriting the winner. No schema migration is needed.

On confirmed success this screen locks, clears the passphrase fields and asks the user to unlock with the new phrase and download a fresh encrypted backup. Failed attempts clear all three change fields. Hiding/locking/unmounting before the derivation finishes prevents a later unsent update; a request already dispatched may still commit, including when its response is lost. If uncertain, refresh and try unlocking with the intended new passphrase before retrying a change.

This is wrapping-passphrase replacement, **not data-key rotation or revocation**. Already-unlocked clients still hold the same master key, and old encrypted backups retain their old passphrase. The existing restore flow rejects an old backup's different wrapper when merging into a store whose wrapper has changed. Keep the old passphrase if old backups are needed and create a fresh backup after changing. Lost old passphrases cannot be bypassed through this action. Account login authorization does not prove knowledge of the passphrase to the server: only the trusted client verifies that the new wrapper holds the same key. A compromised authorized client can still damage data, and this does not add protection against a malicious delivered browser app.

Tests use actual Node Web Crypto to reopen unchanged ciphertext with the new wrapper, reject the old passphrase on the new config, verify old-backup/already-unlocked access remains, and reject wrong owners/modules/passphrases. UI tests cover no plaintext in writes, cleared fields, lock/reopen, wrong current phrase with no write, and late derivation after hidden-page locking. SQLite/API tests cover exact Origin, authentication and ownership, replay/stale conflicts, unchanged entries, property order, expired/revoked/foreign sessions, audit rollback and post-body revocation. These are Node/jsdom tests; actual browser/native and independent review remain pending.

## Atomic private writes and session revocation

Every HTTP initialization, entry save, entry removal and passphrase change passes a server-derived session digest into the private store. After acquiring BEGIN IMMEDIATE, the store rechecks the session's exact account and current expiry before changing data. The mutation and its metadata-only audit event commit in that same transaction; a failed audit leaves the previous configuration, ciphertext, revision and quota state intact. Successful requests produce one audit event, while failed revision/session/quota/config checks produce no success event. The router no longer writes a second audit after the mutation. Internal database/maintenance callers can still use the existing initialize/put/remove signatures without an HTTP-session context; no HTTP request body can select that path. Rewrap always requires its session context.

This serializes commits against session deletion in the same SQLite database. It does not undo a completed write when a session is later revoked, cancel an already completed response, revoke already-held browser encryption keys or make a multi-entry backup restore atomic. Synthetic tests force audit failures at initialization/new save/update/removal, verify preserved configuration/entry/revision, check expired/revoked/foreign sessions for every write and assert exactly one event per successful action through the actual HTTP API.

## Connection failures and retry

Private-store HTTP reads/writes use a 15-second AbortController deadline covering fetch and response-body consumption, with external cancellation preserved for status loading. A failed initial status load now shows an existing UI3 error state and **Retry encrypted-store status** button. Retry only fetches metadata; it does not initialize, unlock, restore or change entries. The prior error clears when retry begins. Unmount aborts the status request, removes listeners/timers and prevents an old response from attaching to another scope.

A timed-out write reports that the change may already have completed and asks the user to lock/unlock to refresh before retrying. Writes are never automatically replayed. Deadline cancellation cannot roll back a server commit or guarantee behavior of a nonconforming browser fetch implementation; local cryptographic/file parsing work has separate bounds and is not governed by this network timer. Tests cover failed-status recovery with GET-only requests, unmount cancellation, stalled reads, uncertain writes, stalled response bodies, pre-cancelled signals, exact cookie/no-store/JSON behavior and timer cleanup. Actual browser/network-device acceptance remains open.

Private-store browser calls now carry X-Locat-Account with their current keyed owner. The server's cookie-derived session reader rejects a different expected owner before serving private metadata or accepting changes. This optional consistency check complements the existing owner/session/transaction/cryptographic scope checks and does not change keys or migrate data.
