# Messaging key continuity and history export

This checkpoint does not enable conversations. Returning browser setup supplies the existing server-bound Ed25519/Curve25519 pins to the local Rust crypto lifecycle. If reopened local keys differ, initialization fails before exposing a bindable session; no private keys or binding pins are silently replaced. The backend binding check remains authoritative as well. Missing local device identity still requires an explicit recovery/migration flow.

After explicit session setup, UI3 offers an encrypted history-key download using shared form controls and matching passphrases (12–1024 characters). The reviewed stack's pinned @matrix-org/matrix-sdk-crypto-wasm 18.9.0 OlmMachine.encryptExportedRoomKeys produces standard armored Megolm session data with 500,000 derivation rounds. No custom export encryption format is introduced. A dedicated same-origin worker keeps derivation off the UI thread; closure cancels it, input is bounded to 16 MiB UTF-8, output to 32 MiB, and a 60-second deadline terminates the worker. No room keys is an explicit unavailable result. Passphrases clear after the operation and on sheet unmount. The download is prepared only after encryption; plaintext keys never enter an anchor, server request or browser storage through this export flow. Ordinary JS strings cannot be guaranteed zeroized.

The encrypted file and passphrase together can decrypt the exported history. Keep the passphrase separately and retain the file privately. This file does not preserve device private identity keys, cross-signing secrets, verification trust, account/session credentials, attachments or missing room keys. Download preparation does not certify that a platform saved the file. Server key backup, complete identity/account recovery and a complete-browser acceptance run remain pending. Existing SDK storage protection is not an OS hardware keystore guarantee.

The isolated Synapse 1.163.0 test now uses fake-indexeddb as a synthetic in-memory adapter with the real Rust IndexedDB store. It stops one client, opens a fresh client against the same adapter/prefix, checks identical device public keys and decrypts historical ciphertext. It also encrypts a real exported room-key set in standard Matrix format, rejects a wrong passphrase, decrypts the file and imports it into a fresh ephemeral crypto identity which decrypts the earlier event. This is real SDK/Rust protocol acceptance over a synthetic storage adapter; it does not prove disk persistence, browser restart/eviction, Android/WebView, native clients or production recovery. The fresh test identity does not reuse/replace the original device identity. No sample user history, passwords or credentials are committed.

Implementation references: installed matrix-js-sdk 44.0.0 CryptoApi.exportRoomKeysAsJson/importRoomKeysAsJson declarations and matrix-sdk-crypto-wasm 18.9.0 OlmMachine export encryption/decryption declarations, published from https://github.com/matrix-org/matrix-js-sdk and https://github.com/matrix-org/matrix-sdk-crypto-wasm . ## Local history import follow-on

After binding a browser device, the UI3 setup sheet now accepts a standard encrypted Matrix history file and its passphrase. File selection alone does not read/decrypt/import it: submission is explicit. Size is checked before reading. A dedicated cancellable worker invokes the pinned Matrix decryptor; no custom cryptographic implementation is used. The import API then calls CryptoApi.importRoomKeysAsJson locally. SDK source inspection confirms this path imports exported room keys through the Rust store, with no plaintext request to Node. There is no new gateway permission or message Send access.

Resource policy: encrypted file at most 32 MiB, decrypted UTF-8 JSON at most 16 MiB, 1–10,000 entries, v1 Megolm armor, supported session algorithm and required bounded fields. Standard public header preflight reads the big-endian derivation count at byte 33 and permits 10,000–2,000,000 rounds; this is a deliberate compatibility limit, not MAC authentication. The Matrix library still authenticates/decrypts the payload. Files using other versions/costs are rejected explicitly. Worker termination bounds decryption to 60 seconds. Raw keys/passphrases are not persisted by the import UI and clear after the attempt/closure; JS memory zeroization cannot be guaranteed. Import may process duplicate entries and the result reports processed entries, not newly restored keys.

History operations are serialized for each open crypto session. Closing cancels decryption, but an SDK store import already in progress may commit; shutdown now waits for pending SDK crypto operations before stopping Rust and releasing the exclusive store lock. The UI explains that boundary and does not claim rollback or cancellation of a committed import. SDK import failures may be partial; no cross-entry atomicity guarantee is made. Imports neither replace device identity nor verify a peer, restore authentication or grant room membership. A fresh bound device can import historical keys without impersonating the old device.

The actual Synapse/Rust test rejects a tampered encrypted key file and wrong password, runs the production preflight against a real export, imports twice into a fresh identity and confirms both historical decryption and unchanged device public keys. Unit/UI tests cover cost/input limits before worker creation, worker-output validation, explicit submission, oversized-file refusal, honest failure and passphrase clearing. A lifecycle test holds the store lock through an in-flight import during close. Real browser file/worker/IndexedDB acceptance remains pending.
