# Production HTTPS Matrix acceptance

`npm run test:matrix` runs both the original isolated protocol tests and `tools/matrix-https-acceptance.mjs`. It requires Node 24+, OpenSSL and the pinned Synapse Python environment documented in tools/matrix-test-requirements.txt. Use `LOCAT_TEST_SYNAPSE_PYTHON=/absolute/venv/bin/python npm run test:matrix`. Linux CI already executes this command after the standard checks; a local pass does not assert remote CI success.

The harness creates a temporary loopback-only Synapse with a new application-service registration and Locat SQLite database. The HTTPS phase launches the actual server/index.mjs on another ephemeral 127.0.0.1 port with a one-day fixture certificate containing an IP SAN. Node's HTTPS client trusts that fixture certificate through its per-request CA option and rejects any different request origin. It does not set NODE_TLS_REJECT_UNAUTHORIZED, disable certificate checks, install a system CA or connect to an existing deployment. The child, SDK clients, temporary registration, database and TLS keys are cleaned up on completion/failure.

The additional phase registers fresh accounts through the production API, logs in with actual scrypt-backed credentials and asserts Secure/HttpOnly/SameSite=Strict cookie attributes. It registers a nonextractable Node WebCrypto P-256 private key, solves the production encrypted device challenge and submits its answer through the real endpoint. Replaying a consumed challenge is rejected. No Locat session/proof/peer/binding authorization callback is replaced in this phase. The browser Link client itself is not executed.

Two verification clients provision normal scoped Matrix sessions through the managed production endpoint, initialize actual Rust crypto using a synthetic IndexedDB adapter and bind public keys through the production endpoint. An accepted relationship is created through contact request/response routes. The actual verification controller obtains peers through the HTTPS peer route, starts restricted sync, exchanges SDK-generated SAS, waits for explicit confirmation on both sides and checks actual stored verified trust. No previous room timelines are exposed by the verification clients.

Negative assertions cover Matrix bearer without Locat login, cookie/bearer without proof, another account's proof, another account's bound token, proof with a different login session for the same account, wrong mutation Origin, blocked-contact peer/key discovery, current managed Matrix-device revocation, Link-key revocation and Locat logout. Managed revocation is also checked directly against Synapse: the previously issued token returns 401. Link revocation immediately blocks Locat gateway access and queues durable managed-device deletion; the test waits for the actual upstream token to return 401. This covers the bound managed device, not every upstream account token. Raw passwords, cookie tokens, proof tokens and Matrix bearer tokens are searched for in the temporary Locat database/WAL and must be absent; this assertion is not a general storage/security audit.

This is production server integration acceptance with synthetic accounts, a Node client and in-memory IndexedDB. It does not validate a real browser's cookie/SameSite behavior, secure-context detection, Web Locks, worker execution, actual settings rendering, browser/disk crypto persistence, complete account/device identity recovery, cross-signing, native platforms, federation, public routing or geographic connectivity. The conversation/Send gate remains closed. Existing direct Matrix and synthetic-guard tests still provide protocol/offline/history coverage.


The schema 14 follow-on also creates two managed devices that never bind: the first is explicitly revoked with only its Locat proof and no token in the command; the second is revoked through Link and its durable cleanup job. Their actual upstream tokens must return 401, their unbound gateway remains 403, and raw-secret database/WAL checks include these accounts.
