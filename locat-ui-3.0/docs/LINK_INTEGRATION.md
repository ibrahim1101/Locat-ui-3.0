# Browser Devices and Locat Link

Schema v7/v8 integrates the original Locat Link proof/pair/transfer design with UI3 accounts and SQLite. This is an experimental browser flow, separate from messaging encryption and native secure storage.

Each browser registers an account-scoped ECDH P-256 identity. Its nonextractable private CryptoKey and peer pins persist in that origin/account's IndexedDB. Concurrent first-use tabs share the winning stored identity. Clearing storage/resetting the key requires new device registration/pairings; it does not revoke a key on the server automatically. At most 50 historical identities/account can register. Registering an already revoked canonical public key is rejected; base64 aliases cannot bypass revocation.

Every protected command/list needs both a valid account cookie and a private-key proof bound to that exact account/session/device. A server ECDH/HKDF/AES-GCM challenge expires after 60 seconds and is consumed on every attempt. Proof tokens expire after ten minutes, are held only in client memory, and expire on server restart. Proof maps are bounded. All mutations require the exact trusted Origin and are rate-limited. The browser renews proof before expiry and sends a heartbeat only while this view is active; recent browser activity is not native/background presence.

Pairing starts between two active devices owned by the same account. Both screens derive a 40-bit hexadecimal comparison code from the pair ID and sorted canonical public keys. Approval is manual and required from both proved private-key holders. Device aliases are not proof. Client peer pins must match before sending/receiving; a verified server row alone is insufficient. Actual Chromium two-context comparison/consent acceptance now passes in isolated CI (see BROWSER_FOUNDATION_ACCEPTANCE.md). Independent review and physical-device comparison remain necessary. This is not a universally compatible or audited messenger protocol.

Link's pair/account-derived AES-GCM key encrypts text, HTTP/HTTPS URL text, explicit clipboard text and files. Fresh IVs and authenticated context bind account, pair, immutable transfer ID, device direction, kind, file metadata, size/chunk count and chunk position. There is no automatic clipboard monitoring or automatic execution/navigation of received URLs.

Files are bounded at 200 MiB and uploaded in 256 KiB plaintext chunks. Text is bounded at 64 KiB UTF-8. Sender buffering is one chunk; receiver buffering may reach the full file size before the browser download. The server reserves up to 256 MiB pending plaintext-size budget and 100 pending deliveries/account, verifies exact ciphertext/chunk lengths and permits idempotent re-publication of an identical chunk. Chunk writes allow 4000/minute/account; other commands allow 60/minute/account. HTTP client calls time out after 15 seconds. No resumable upload guarantee: after interruption, cancel the incomplete transfer and resend. The stop button cancels after the in-flight chunk returns.

Receiver-only reads and receipt actions are enforced server-side. UI receipt controls enable only after local payload authentication; receipt acknowledges the user/device action, not guaranteed filesystem save or human reading. Queued means persisted ciphertext, not delivered. Source can cancel; only destination may complete. Completion/cancellation deletes active chunk ciphertext and retains delivery metadata. Rejecting a pair or revoking a device invalidates its pair access, cancels pending jobs and removes their chunks. Revocation cannot recall downloaded copies, clipboard history, browser memory or backups, and does not sign out independent account sessions.

Names, MIME labels, file sizes, device labels, routing and timestamps are server-readable; contents are encrypted by the client. Metadata retention/redaction, cryptographic erasure of backups, native keychain/keystore, LAN/mDNS/P2P discovery, cross-device media source consent/discovery, native background transport and Remote capture/control remain open. A trusted HTTPS/localhost browser with Web Crypto and IndexedDB is required. Browser or origin compromise can access stored device keys and unlocked content.

Source: original Locat integration/ui3, 2e394921377fef687d565cff3208d36dd6a56b80, api/linkProof.ts, api/linkRouter.ts and src/lib/link.ts. UI3 uses different authenticated account/transfer domains and does not silently import original device identities/pairings/transfers. GPL provenance is retained.

## Lifecycle and delayed-request authorization

The live Devices subtree is keyed by authenticated account, so dialogs, drafts, private-key references, proof state and verified-receipt state cannot carry into another account. Leaving the subtree aborts outstanding HTTP requests; the helper rejects already-aborted work and bounds fetch plus body decoding to 15 seconds. A synchronous operation guard prevents duplicate action submission; background polling skips active user operations. A timed-out mutation is explicitly uncertain and never automatically retried. Cancellation cannot undo a request already committed on the server.

The server rechecks the same live Locat session and active proof/device after every awaited Link/Remote request body, and rechecks asynchronous registration key validation/challenge generation before returning/committing. This closes the authenticated-before-body revocation window. These HTTP boundary checks do not claim database transaction fencing across independent server processes or instant recall of already completed actions. Matrix gateway upstream waits retain their separate authorization checks. Regression tests pause bodies before revoking sessions, proofs or device keys and assert that no rename, pairing, transfer or Remote mutation follows.
